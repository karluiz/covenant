# 3.26 — Operator MCP Clients

## Goal

An operator can call tools from user-configured MCP servers directly in
its own LLM loop — "check the staging health endpoint via the infra MCP"
works without delegating to a `dispatch_acp` executor.

## Context

Today the operator loop (`teammate/llm.rs`) has only native Rust tools.
MCPs reach executors two ways (Covenant MCP server injected into ACP
spawns + the harness's own config), but the operator itself has no MCP
client. `rmcp` 2.2.0 is already a dependency (server side); its `client`
feature closes the gap without a new crate.

The Anthropic-hosted MCP connector (`mcp_servers` in the Messages API)
was rejected: it connects from Anthropic's servers, so localhost / LAN
MCPs are unreachable. The client must run in-app.

## Design

### Config — two halves, mirroring `gh_*`

1. **Server definitions: global, in `config.json`** (same security
   posture as provider API keys, which already live there):

   ```jsonc
   "mcpServers": [
     { "name": "infra", "url": "http://127.0.0.1:9400/mcp",
       "headers": { "Authorization": "Bearer ..." } }
   ]
   ```

   HTTP (streamable-http) transport ONLY in v1. No stdio: spawning
   arbitrary child processes from operator config is a command-execution
   surface and needs its own safety review.

2. **Per-operator allowlist: registry-only field** (like `acp_enabled`,
   NOT SOUL frontmatter):

   ```rust
   /// Names of config-level MCP servers this operator may call.
   /// Empty = no MCP tools registered (deny-biased).
   #[serde(default)]
   pub mcp_servers: Vec<String>,
   ```

### Client + loop wiring

- New `teammate/mcp_client.rs`: connect (streamable-http + Bearer),
  `tools/list`, `tools/call`. `rmcp` client feature; no persistent pool
  in v1 — connect at dispatch, drop at end of turn.
- `ToolEnv` gains `mcp: Vec<McpConn>` (built in `commands.rs` alongside
  the GitHub keychain read; per-server connect+list timeout ~3s,
  failures log + skip, never block the dispatch).
- Tool names namespaced `mcp__<server>__<tool>`, merged into
  `all_tool_defs`; `execute_tool` routes the prefix to the client.
- Tool RESULTS pass through `safety::mask_secrets` before entering the
  LLM turn (same rule as `session_output`). Cap result size like
  `format_acp_report` (~4000 chars).

### Safety posture

- Deny-biased: no servers allowed until the user edits the operator.
- MCP tools execute with operator authority and have arbitrary side
  effects; that is accepted at the same trust level as `gh_*` write
  access — the gate is the per-operator allowlist, granted by the
  principal in the editor.
- The Covenant MCP server itself is NOT auto-attached to operators:
  its tools (tasks/notes/sessions) already exist as native operator
  tools; attaching it would duplicate names.

### UI

Operator editor: an "MCP servers" section listing config-level servers
with per-operator checkboxes (renders only when `config.mcpServers` is
non-empty). Settings → a plain list editor for `config.mcpServers`
(name, url, headers). Follow rail/row homologation; sharp corners.

## Out of scope

- stdio / child-process MCP transport (needs safety review first).
- Tool-level allowlists inside a server (v1 is per-server all-or-none;
  Reflexes-level `ALWAYS-YES` per tool is a follow-up).
- Persistent connection pool, reconnect, health UI.
- OAuth flows for remote MCPs — headers only.
- Injecting these user MCPs into ACP executor spawns (harness config
  already covers executors).
- Any change to `crates/agent/src/safety.rs` or the exec policy
  framework.

## Acceptance criteria

- [ ] A server in `config.mcpServers` + checked on an operator →
      its tools appear namespaced in the operator's tool defs and a
      dispatch can call one end-to-end (integration test against an
      in-process rmcp server).
- [ ] Operator with empty `mcp_servers` sees zero MCP tools and a
      forged `mcp__*` call is refused (mirrors the `dispatch_acp` gate
      test).
- [ ] Unreachable server: dispatch still completes; skip is logged.
- [ ] MCP tool results are secret-masked and size-capped before the
      LLM turn.
- [ ] `cargo test -p covenant --lib teammate` and `npm test` green.

## File boundaries

- **Create**: `crates/app/src/teammate/mcp_client.rs` (≤ ~300 lines
  incl. tests)
- **Touch**: `teammate/tools.rs`, `teammate/llm.rs`,
  `teammate/commands.rs`, `operator_registry.rs`, config load/save,
  `crates/app/Cargo.toml` (rmcp features), `ui/src/api.ts` +
  operator editor + settings surface
- **DO NOT touch**: `crates/agent/src/safety.rs`, `mcp_server.rs`
  (server side stays as is), ACP spawn injection paths

## Complexity

`medium` (2–3 sessions: 1 client+wiring, 1 config+UI, 1 polish/tests).

## Open questions

- Headers with tokens in `config.json`: acceptable now (precedent:
  provider keys), or keychain from day one?
